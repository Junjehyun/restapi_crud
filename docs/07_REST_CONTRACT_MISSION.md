# REST 계약 미션북

| 항목 | 내용 |
|------|------|
| 대상 | 보험상품 + 고객 + **설계사** CRUD 를 끝낸 사람 |
| 목표 | 새 도메인을 또 만들지 않고, **React + TypeScript + Spring Boot REST** 의 미시 감각을 스스로 채운다 |
| 방식 | 개념(교과서) → 아주 쉬운 설명 → **네가 푸는 미션**. 정답 코드는 이 문서에 없다 |
| 연습 소재 | 이미 있는 **고객(Customer)** 먼저, 마지막에 **보험상품**(그리고 설계사)으로 같은 패턴을 옮긴다 |
| 이전 문서 | `06_CONSULTANT_CRUD_MISSION.md` — 설계사 CRUD 가 안 끝났으면 여기 오지 않는다 |
| 관련 | `00_README.md` · `02_ROADMAP.md` · `03_SPA.md` |
| 하지 않는 것 | 네 번째 도메인 CRUD, 로그인/JWT, 주문, 결제 |

---

## 0. 이 문서가 이전 매뉴얼과 다른 점

상품·고객은 선생님이 코드를 보여 줬다.  
설계사 CRUD(`06_CONSULTANT_CRUD_MISSION.md`)는 같은 CRUD를 **네가 썼다.**  
이 문서는 그 **다음**이다. 새 테이블 없이, 있는 API를 계약으로 다듬는다.

| | 상품·고객 매뉴얼 | 설계사 CRUD 미션 | 이 문서 (REST 계약) |
|--|------------------|------------------|---------------------|
| 누가 코드를 쓰나 | 문서가 거의 다 줌 | **네가 씀** | **네가 씀** |
| 배우는 것 | 층이 있고, 파일이 짝이다 | 그 층을 빈 파일에서 재현 | 한 줄이 **왜** 있는지, JSON이 **계약**인지 |
| 새 테이블 | 상품 → 고객 | 설계사 | **없음**. 있는 API를 진짜 REST 답게 만든다 |
| 막히면 | 부록 복붙 | 힌트 + 기존 파일 | 힌트만 보고, 그래도 안 되면 **개념만** 질문 |

### 나와(Grok)의 역할

이 순환을 같이 할 때 규칙은 이렇다.

- 물어보면 **개념·방향·힌트** 는 준다.
- “이 파일 전체 코드 짜 줘”, “복붙할 예제 줘” 에는 **답을 주지 않는다.**
- 네가 쓴 코드를 가져오면, 틀린 줄이 어디인지·왜인지를 같이 본다.

---

## 1. 왜 (지금 단계에서는) 또 CRUD가 아니고, 왜 아직 로그인이 아닌가

> 설계사 CRUD 는 **이미 끝난 상태**라고 가정한다. 안 끝났으면 `06_CONSULTANT_CRUD_MISSION.md` 로 돌아가라.

목표를 다시 적는다.

> Laravel MVC 감각에서 벗어나, **TypeScript + React + Spring Boot REST** 조합을 손으로 이해한다.

이미 가진 것:

- 층 나누기 (Controller → Service → Repository)
- DTO로 JSON 주고받기
- React 페이지에서 axios 호출, 목록/등록/수정/삭제

아직 없는 것 (그래서 REST를 “쓰는 사람”이지 “설계하는 사람”이 아님):

| 구멍 | 지금 코드에서 실제로 일어나는 일 |
|------|----------------------------------|
| 서버 검증 | `CustomerRequest` 에 규칙이 없다. 이름 없이 POST 해도 일단 들어간다. |
| 에러 JSON | 없는 id 조회는 `IllegalArgumentException` → 브라우저/Postman 에는 **500** 에 가깝게 보인다. |
| GET 의 능력 | `findAll()` 만 있다. 이름 검색, 상태 필터가 없다. |
| 프론트 에러 | `CustomerCreate` 는 실패하면 **항상 같은 한글 문장**만 보여 준다. 서버가 왜 거절했는지 화면에 안 나온다. |
| 의존성 | `build.gradle` 에 웹·JPA 만 있다. 검증용 starter 는 아직 없다. |

네 번째 도메인(계약, 주문)을 또 만들면 층 그림만 반복된다. 설계사로 세 번째는 이미 그렸다.  
로그인을 지금 붙이면 “검증 버그인지, 토큰 버그인지”를 구분하지 못한다.  
`02_ROADMAP.md` 의 2단계(인증)는 **이 순환이 끝난 다음**이다.

이번 순환의 한 줄:

> **성공 응답만 알던 API를, 실패·검색까지 포함한 계약으로 만든다.**

## 2. 이 문서 쓰는 법

각 유닛은 같은 네 덩어리다.

1. **개념** — 무엇을 왜 배우는지 (교과서)
2. **아주 쉽게** — 아이한테 말하듯
3. **라라벨로 번역** — 이미 아는 자리에 얹기
4. **미션** — 네가 코드를 고친다. 완료 기준을 스스로 체크

규칙:

- **한 유닛을 끝낸 뒤에만** 다음으로 간다. 하루에 유닛 하나면 충분하다.
- 미션마다 아래 세 줄을 메모한다. (학습 일기)

```
한 일:
막힌 줄:
아직 모르는 단어:
```

- 정답은 Postman + 브라우저가 알려 준다. 문서가 알려 주지 않는다.
- 고객으로 먼저 하고, **유닛 6** 에서 상품에 같은 것을 옮긴다. 옮길 수 있어야 “습득”이다.

### 이 순환이 끝났다고 말하는 기준

- [ ] 이름 없는 고객 POST → **400** + 필드 에러 JSON
- [ ] 없는 id GET/PUT/DELETE → **404** + 약속된 에러 JSON (500 아님)
- [ ] 같은 이메일로 두 번 등록 → **409** + 에러 JSON
- [ ] `GET /api/customers?name=김` 이 검색된다
- [ ] 등록 폼이 **서버가 준 메시지**를 화면에 보여 준다
- [ ] 없는 고객 수정 URL로 들어가면, 사람이 읽는 안내가 나온다
- [ ] 보험상품에도 검증 + 404 가 **네가 스스로** 붙어 있다
- [ ] 기존 상품/고객 행복 경로(등록·수정·삭제)가 그대로 된다

---

## 3. 머릿속에 넣을 한 장

MVC(라라벨 Blade)에서 폼이 틀리면:

```
서버가 HTML을 다시 그려서 보낸다
  → 빨간 글자가 페이지에 이미 박혀 있다
```

REST + React 에서는:

```
서버는 JSON 과 상태 코드만 보낸다
  → 화면은 React 가 그 JSON 을 읽고 직접 그린다
```

그래서 이번 순환의 주인공은 화면이 아니라 **계약**이다.

```
[ React 폼 ]
    │  POST /api/customers
    │  { "name": "", "email": "a@b.com", ... }
    ▼
[ Controller ]  검증 실패? → 400 + { 필드: 이유 }
    │  통과하면
    ▼
[ Service ]     이메일 이미 있음? → 409 + { 메시지 }
                없는 id?         → 404 + { 메시지 }
    │  정상만
    ▼
[ Repository / DB ]
    │
    ▼
[ Response DTO ] 201 / 200 / 204
    │
    ▼
[ React ]  status 와 body 를 읽어 화면을 바꾼다
```

성공만 다루던 2번째와 달리, **실패도 계약**이다.

# 유닛 0. 워밍업 — 지금 코드를 관찰만 한다

코드는 **한 줄도 고치지 않는다.**  
3번째의 근육은 “쓰기” 전에 “무엇이 비었는지 보기”다.

## 개념

아는 것과 할 수 있는 것은 다르다.  
두 바퀴를 돌면 “파일이 어디에 있는지”는 안다.  
아직 모르는 것은 “이 요청이 실패하면 누가, 어떤 JSON을 주는지”다.

## 아주 쉽게

숙제를 두 번 베껴 쓰면, 답안지 위치는 외워진다.  
시험에 비슷한 문제가 변형되어 나오면 손이 멈춘다.  
지금은 답안지를 덮고, **빈칸이 어디인지** 동그라미만 친다.

## 라라벨로 번역

`php artisan route:list` 를 보고 “라우트는 있네” 하는 것과 같다.  
아직 validation, 404 JSON, query string 은 안 붙여 본 상태다.

## 미션 0

Postman(또는 curl)으로 아래를 **실제로** 치고, 상태 코드와 body 를 노트에 적는다.

1. `POST /api/customers`  body: `{ "name": "", "email": "", "phone": "" }`
2. `GET /api/customers/999999`  (없는 id)
3. `GET /api/customers`
4. 브라우저 개발자 도구 Network 탭을 연 채, 고객 등록 화면에서 이름만 비우고 제출한다.  
   요청이 **서버까지 갔는가, 프론트에서 막혔는가?**

메모 칸:

| 요청 | 상태 코드 | body 모양 (한 줄) | 누가 거절했나 (프론트 / 서버 / 모름) |
|------|-----------|-------------------|--------------------------------------|
| 빈 POST | | | |
| 없는 id | | | |
| 목록 GET | | | |
| 화면에서 빈 이름 | | | |

**완료 기준**

- [ ] 위 표가 비어 있지 않다
- [ ] “빈 이름 제출이 서버까지 가는가”에 네/아니오로 답했다

**힌트 (정답 코드 아님)**

- 프론트 `CustomerCreate.tsx` 의 `handleSubmit` 앞부분을 읽어 보라. `return` 이 있으면 서버를 안 부른다.
- 서버 예외가 나면 콘솔/`bootRun` 로그에 스택이 길게 찍힌다. 그게 500의 냄새다.

# 유닛 1. HTTP 상태 코드는 계약이다

## 개념

REST에서 상태 코드는 “잘 됐나?”의 **공통 언어**다.  
프론트는 body 문장을 읽기 전에, 먼저 숫자로 분기한다.

이 프로젝트에서 이미 쓰는 성공 코드:

| 코드 | 이미 쓰는 곳 | 뜻 |
|------|--------------|----|
| 200 | GET, PUT | 성공, body 있음 |
| 201 | POST 등록 | 새로 만들었다 |
| 204 | DELETE | 성공, body 없음 |

이번에 의식적으로 쓸 실패 코드:

| 코드 | 뜻 | 우리 예 |
|------|----|---------|
| 400 | 요청이 잘못됨 (형식·검증) | 이름 없음, 이메일 형식 아님 |
| 404 | 그 자원이 없음 | 없는 id |
| 409 | 지금 상태와 충돌 | 이메일 중복 |
| 500 | 서버가 예상 못한 사고 | 우리가 예외를 안 잡은 경우 |

**핵심:** 없는 고객을 500으로 주면, 프론트는 “네트워크가 터졌다”와 “그 사람이 없다”를 구분하지 못한다.

## 아주 쉽게

식당에 전화를 건다.

- 200: “네, 예약됐어요. 정보 불러 드릴게요.”
- 201: “새 예약 만들었어요.”
- 204: “취소했어요. 더 말할 거 없어요.”
- 400: “이름이 안 들려요. 다시 말해 주세요.”
- 404: “그 번호의 예약은 없어요.”
- 409: “그 시간에 이미 예약이 있어요.”
- 500: 주방에서 불이 났다. 손님이 뭘 잘못한 게 아니다.

손님(프론트)은 주방이 아니라 **전화기 너머 숫자**로 다음 행동을 정한다.

## 라라벨로 번역

| 여기 | 라라벨 |
|------|--------|
| `ResponseEntity.status(CREATED)` | `return response()->json(..., 201)` |
| `noContent()` | `response()->noContent()` (204) |
| 검증 실패 400 | `FormRequest` 실패 시 422 (라라벨 기본). REST에서는 400 또는 422 둘 다 쓰인다. **이 순환은 400으로 통일**한다. |
| 없는 모델 404 | `abort(404)` / `findOrFail` |

라라벨은 422를 많이 쓴다.  
우리는 초보 계약을 단순하게 하려고 **검증 실패 = 400** 으로 고정한다. 나중에 바꿔도 된다.

## 미션 1

코드를 거의 안 고쳐도 된다. **관찰 + 한 줄 약속**이 미션이다.

1. 유닛 0 표의 상태 코드를, 위 식당 비유로 다시 해석한다.  
   “지금 없는 id 는 식당에서 몇 번을 말하고 있나?”
2. 노트에 **우리 API 계약 초안**을 손으로 쓴다. (구현 전)

```
POST   /api/customers           성공 ___ / 검증실패 ___ / 이메일중복 ___
GET    /api/customers/{id}      성공 ___ / 없음 ___
PUT    /api/customers/{id}      성공 ___ / 없음 ___ / 검증실패 ___
DELETE /api/customers/{id}      성공 ___ / 없음 ___
GET    /api/customers?name=     성공 ___   (유닛 4에서 구현)
```

3. `CustomerController` 를 열고, 성공 코드가 **어느 줄에서** 정해지는지 파일명+메서드만 적는다.

**완료 기준**

- [ ] 계약 초안의 빈칸을 숫자로 채웠다
- [ ] 없는 자원과 잘못된 입력을 **다른 숫자**로 쓰겠다고 적어 두었다
- [ ] 201 / 204 를 왜 쓰는지 한 문장으로 말할 수 있다

**힌트**

- Controller 의 `ResponseEntity.status(...)`, `ok()`, `noContent()` 를 찾아라.
- Service 의 `orElseThrow` 는 지금 상태 코드를 정하지 않는다. 예외만 던진다. 그 차이를 기억하라.

# 유닛 2. 서버가 입력을 검사한다

## 개념

검사를 두 곳에서 할 수 있다.

| 층 | 하는 일 | 한계 |
|----|---------|------|
| React (`if (!name.trim())`) | 빨리 막아 준다. 입력칸 옆이 편하다 | 우회 가능 (Postman, 다른 클라이언트) |
| Spring Request DTO | **진짜 문지기**. 모든 클라이언트가 통과해야 한다 | 화면 문구는 React가 다시 그려야 한다 |

REST의 원칙:

> 서버는 클라이언트를 믿지 않는다.  
> 프론트 검사는 친절, 서버 검사는 계약.

필요한 조각 (이름은 네가 검색한다):

1. Request DTO 필드에 “비면 안 됨”, “이메일 형식” 같은 **제약**
2. Controller 가 그 제약을 **켜는** 스위치
3. 실패했을 때 나가는 JSON 모양 (유닛 3과 이어짐)
4. 그걸 쓰려면 `build.gradle` 에 **검증용 의존성**이 있어야 한다. 지금은 없다.

권장 검증 (고객):

| 필드 | 규칙 |
|------|------|
| name | 비어 있으면 안 됨 |
| email | 비어 있으면 안 됨 + 이메일 형식 |
| phone | 비어 있으면 안 됨 |
| birthDate, address, status | 없어도 됨 |

상품은 유닛 6에서 네가 규칙을 정한다.

## 아주 쉽게

학교 앞 가게 규칙.

- 친구가 “야, 이름 써” 하고 막아 주는 것 = 프론트 검사. 착하다. 뒷문으로 들어가면 소용없다.
- 선생님 책상에 “이름 없는 종이 받지 마” 라고 적혀 있는 것 = 서버 검사.  
  Postman으로 와도, 다른 앱이 와도, 선생님은 같은 이유로 거절한다.

거절할 때는 “안 돼”만 외치지 말고,  
“이름 칸이 비었어” 라고 **칸 이름과 이유**를 적어 돌려준다. 그게 400 JSON 이다.

## 라라벨로 번역

| 여기 | 라라벨 |
|------|--------|
| Request DTO 의 제약 어노테이션 | `FormRequest` 의 `rules()` |
| Controller 에서 검증을 켜는 어노테이션 | FormRequest 를 타입힌트하면 자동 실행 |
| 실패 시 필드별 메시지 JSON | `$errors` / 422 JSON (`errors.name: [...]`) |

라라벨은 FormRequest 만 만들어도 검증이 돈다.  
Spring 은 DTO 에 규칙만 적으면 부족하고, **Controller 에서 검증을 켜 줘야** 한다. 이 차이를 미션에서 직접 확인하라.

## 미션 2

대상 파일 (힌트일 뿐, 네가 더 건드려도 됨):

- `build.gradle`
- `src/main/java/com/yama331/restapi_crud/dto/CustomerRequest.java`
- `src/main/java/com/yama331/restapi_crud/controller/CustomerController.java`

할 일:

1. 검증을 쓰려면 어떤 의존성이 필요한지 찾아 **추가**한다. 서버를 재시작한다.
2. `CustomerRequest` 에 name / email / phone 규칙을 붙인다.
3. 등록·수정 Controller 메서드에서 검증을 켠다.
4. Postman으로 확인한다.

   ```
   POST /api/customers
   { "name": "", "email": "not-an-email", "phone": "" }
   ```

5. **아직** `@ControllerAdvice` 를 만들지 마라.  
   지금 단계의 관찰 질문: 검증을 켠 직후 상태 코드와 body 가 유닛 0 때와 어떻게 달라졌는가?

**완료 기준**

- [ ] 위 POST 가 DB에 저장되지 않는다
- [ ] 응답이 201이 아니다
- [ ] body 어딘가에 `name` 또는 `email` 이라는 필드 이름이 보인다
- [ ] 올바른 JSON 으로 POST 하면 예전처럼 201 + 고객이 생긴다
- [ ] 프론트 등록 화면의 **정상 등록**도 여전히 된다

**힌트**

- 검색어: `spring boot validation starter`, `@Valid`, `@NotBlank`, `@Email`, `@RequestBody`.
- `@NotNull` 과 `@NotBlank` 의 차이를 한 줄로 적어라. 빈 문자열 `""` 이 핵심이다.
- 수정(`PUT`)에도 같은 스위치를 켜라. 등록만 검사하고 수정은 안 하면 계약이 구멍 난다.
- 의존성을 안 넣으면 어노테이션을 붙여도 조용히 무시되거나 컴파일이 안 된다. 둘 중 어떤지 직접 보라.

# 유닛 3. 예외를 JSON 계약으로 바꾼다

## 개념

지금 Service 는 없는 id 에 `IllegalArgumentException` 을 던진다.

```99:104:src/main/java/com/yama331/restapi_crud/service/CustomerService.java
        Customer customer = customerRepository.findById(id)
            .orElseThrow(() -> new IllegalArgumentException(
                "해당 고객이 없습니다. id=" + id
            ));
        return CustomerResponse.from(customer);
```

주석에도 적혀 있다. “나중에 `@ControllerAdvice` 로 404 JSON 을 예쁘게 만들 수 있음.”  
그 나중이 **지금**이다.

하고 싶은 계약:

| 상황 | 상태 | body 에 꼭 들어갈 것 |
|------|------|----------------------|
| 검증 실패 | 400 | 필드 이름 + 이유들 |
| 없는 고객/상품 | 404 | 사람이 읽는 메시지, 가능하면 경로 |
| 이메일 중복 (유닛 7) | 409 | 사람이 읽는 메시지 |
| 그 외 진짜 사고 | 500 | 너무 자세한 스택은 숨긴다 |

에러 body 모양을 **네가 먼저 종이에 고정**한다. 예시는 힌트일 뿐, 복붙 강제 아님.

권장 초안 (바꿔도 된다. 한 번 정하면 프론트와 맞춰야 한다):

```json
{
  "status": 404,
  "message": "해당 고객이 없습니다. id=999",
  "errors": null
}
```

```json
{
  "status": 400,
  "message": "입력값이 올바르지 않습니다.",
  "errors": {
    "name": "비어 있을 수 없습니다.",
    "email": "이메일 형식이 아닙니다."
  }
}
```

`errors` 는 검증 실패에만 채운다.

구현에서 결정할 것:

1. 공통 에러 응답 클래스 (DTO)
2. “없음”을 나타내는 **우리 예외** (그냥 `IllegalArgumentException` 을 404로 매핑해도 되고, `NotFoundException` 을 만들어도 된다. 장단을 메모하라)
3. 모든 Controller 의 예외를 한곳에서 잡는 클래스
4. 검증 실패 예외(`MethodArgumentNotValidException` 계열)도 같은 JSON 으로

## 아주 쉽게

지금까지는 주방에서 접시가 깨지면, 손님에게 깨진 접시 더미를 그대로 들고 나갔다 (스택 트레이스, 500).

이제 홀 매니저를 한 명 둔다.

- 주방에서 무슨 일이 나도, 매니저가 **짧은 메모지**로 바꿔 손님에게 준다.
- “예약 없음” 메모, “이름 다시 쓰세요” 메모, “이미 그 자리 찼어요” 메모.
- 손님은 메모 종류만 보면 된다. 주방 기계 이름을 몰라도 된다.

그 매니저가 `@ControllerAdvice` 다.

## 라라벨로 번역

| 여기 | 라라벨 |
|------|--------|
| `@ControllerAdvice` + `@ExceptionHandler` | `app/Exceptions/Handler.php` / `bootstrap/app.php` 의 `withExceptions` |
| 커스텀 `NotFoundException` | `ModelNotFoundException` → 404 |
| 검증 예외를 JSON 으로 | FormRequest 실패 시 JSON `errors` |
| 에러 Response DTO | 직접 만든 error resource, 또는 배열 |

## 미션 3

1. 에러 JSON 모양을 노트에 확정한다. (프론트 유닛 5가 이 모양을 믿는다)
2. 공통 에러 응답 클래스를 만든다.
3. 전역 예외 처리 클래스를 만든다.
4. 없는 id 의 GET / PUT / DELETE 가 **404 + 그 JSON** 이 되게 한다. 500이 되면 실패.
5. 유닛 2의 빈 POST 가 **400 + 필드 errors** 가 되게 한다. Spring 기본 에러 HTML/기본 JSON 이 그대로면 아직 미완.
6. 상품 API는 아직 손대지 않는다. (유닛 6)

확인:

```
GET /api/customers/999999
POST /api/customers   { "name":"", "email":"x", "phone":"" }
GET /api/customers/1     ← 있는 id 는 예전처럼 200
```

**완료 기준**

- [ ] 없는 id → 404, body 가 네가 정한 모양
- [ ] 검증 실패 → 400, `errors` 에 필드가 보인다
- [ ] `bootRun` 로그에 스택이 손님 응답으로 그대로 나가지 않는다
- [ ] 정상 CRUD 가 깨지지 않았다

**힌트**

- 검색어: `@RestControllerAdvice`, `@ExceptionHandler`, `MethodArgumentNotValidException`, `FieldError`, `ResponseEntity`.
- `IllegalArgumentException` 을 전부 404로 바꾸면, 나중에 “잘못된 인자”와 “없음”이 섞인다. 그래서 별도 예외를 권한다. 강제는 아니다.
- 패키지 이름은 `exception` 이든 `common` 이든 네가 정해라. Controller가 Repository를 부르지 않는 규칙만 지켜라.
- 예외 처리 클래스를 만들어도 안 잡히면, 컴포넌트 스캔 패키지(`com.yama331.restapi_crud`) 안에 있는지를 보라.

# 유닛 4. 조회는 findAll 이 전부가 아니다

## 개념

`GET /api/customers` 는 “전부 줘”다.  
데이터가 늘어나면 프론트에서 `filter` 해도 되지만, 그건 **서버가 할 일**을 브라우저에 떠넘기는 것이다.

REST의 GET 은 몸통(body) 대신 **쿼리 문자열**로 조건을 실어 보낸다.

```
GET /api/customers              → 전체
GET /api/customers?name=김      → 이름에 "김"이 들어간 사람
GET /api/customers?status=활성  → 활성만
GET /api/customers?name=김&status=활성
```

필요한 조각:

| 층 | 할 일 |
|----|--------|
| Controller | URL 의 `name`, `status` 를 메서드 인자로 받는다. 없으면 `null` |
| Service | “조건이 있으면 검색, 없으면 전체” |
| Repository | **메서드 이름만** 적으면 Spring Data 가 SQL 을 만든다 |
| 프론트 | 검색칸 state + API 함수에 파라미터 + 목록 다시 그리기 |

페이지네이션(`page`, `size`)은 **이번 순환에서 하지 않는다.**  
한 가지(검색/필터)만 붙인다. 페이지는 인증 이후에도 늦지 않다.

## 아주 쉽게

도서관에 가서 “책 다 주세요” 하면, 사서가 트럭을 끌고 온다. 그게 `findAll` 이다.

“김씨 저자만요” 하면 사서가 **뒷방에서 골라** 가져온다.  
손님이 트럭을 뒤지는 게 아니다.

쿼리 문자열 `?name=김` 은 사서에게 건네는 쪽지다.  
쪽지가 없으면 예전처럼 전부 준다. **기존 목록 화면이 안 깨져야** 한다.

## 라라벨로 번역

| 여기 | 라라벨 |
|------|--------|
| `@RequestParam(required = false) String name` | `$request->query('name')` |
| `findByNameContaining(String name)` | `Customer::where('name', 'like', "%$name%")` |
| 메서드 이름 → SQL | Eloquent 스코프 / 쿼리 빌더. Spring 은 이름 규칙이 마법처럼 동작한다 |

Repository 에 `List<Customer> findByNameContainingIgnoreCase(String name);` 처럼 **이름만** 적는 순간, 구현 클래스 없이 LIKE 검색이 생긴다.  
유닛의 핵심 경험이다. 꼭 SQL 로그(`show-sql` 은 이미 켜져 있다)로 확인하라.

## 미션 4

백엔드 먼저, 프론트는 그 다음. **Postman이 통과하기 전에 화면을 건드리지 마라.**

백엔드:

1. `CustomerRepository` 에 이름 검색 메서드를 이름만 추가한다. (구현 클래스 만들지 마라)
2. 가능하면 `status` 정확 일치도 추가한다.
3. `findAll` 을 “파라미터 있으면 검색, 없으면 전체”로 바꾸거나, 별도 메서드로 나누고 Controller 에서 고른다. 선택은 네가 한다. 이유를 일기에 적어라.
4. Postman:

   ```
   GET /api/customers
   GET /api/customers?name=김
   GET /api/customers?status=활성
   GET /api/customers?name=없는이름xyz
   ```

   마지막은 **200 + 빈 배열** 이어야 한다. 404가 아니다.  
   “목록이 비었다”와 “그 자원이 없다”는 다르다.

프론트 (`CustomerList.tsx`, `customerApi.ts`):

5. 이름 검색 입력칸 + 검색 버튼 (또는 입력 후 조회).
6. `getCustomers` 가 쿼리를 실어 보낸다.
7. 결과가 0건이면 “검색 결과가 없습니다” 와 전체 0건을 구분하면 더 좋다. 필수는 아님.
8. 검색을 지우면 다시 전체가 나온다.

**완료 기준**

- [ ] `?name=` 없이 목록이 예전과 같다
- [ ] 있는 이름 조각으로 검색하면 그 행만 온다
- [ ] 없는 이름 → 200 + `[]`
- [ ] 터미널 SQL 로그에 `like` 또는 `where` 가 보인다
- [ ] 브라우저 고객 목록에서 검색이 된다

**힌트**

- 검색어: `Spring Data JPA query method`, `Containing`, `IgnoreCase`, `@RequestParam`, axios `params`.
- axios 는 두 번째 인자로 `{ params: { name } }` 를 넘길 수 있다. 쿼리를 문자열로 직접 이어 붙이지 마라.
- `name` 이 빈 문자열 `""` 일 때 서버가 LIKE `%%` 로 전체를 줄지, 무조건으로 볼지는 Service 에서 정하라.
- 목록 함수를 나누면 (`getCustomers` / `searchCustomers`) 프론트가 두 번 갈라진다. 한 함수 + optional 파라미터가 보통 더 단순하다.

# 유닛 5. TypeScript 는 DTO 의 쌍둥이다

## 개념

백엔드가 에러 JSON 계약을 정했으면, 프론트는 **그 모양을 타입으로 적어야** 한다.

지금:

```62:64:frontend/src/pages/CustomerCreate.tsx
    } catch(err) {
      console.error(err);
      setError('고객 등록에 실패했습니다. 네트워크 탭과 서버 로그를 확인하세요.');
```

서버가 뭐라고 말했든, 화면은 같은 문장이다.  
이건 REST가 아니라 “실패하면 빨간 줄”이다.

이번 유닛의 목표:

1. 에러 응답 타입을 TypeScript 로 적는다. (유닛 3에서 정한 모양과 **필드 이름 동일**)
2. axios 에러에서 `response.status` 와 `response.data` 를 꺼내는 법을 한곳에 모은다.
3. 등록/수정 화면이 400 이면 `errors` 를, 409 면 `message` 를 보여 준다.
4. 수정 화면이 404 이면 “없는 고객”을 사람이 읽게 한다. 빈 폼을 보여 주면 안 된다.

행복 경로 타입은 이미 잘 되어 있다.

```20:27:frontend/src/types/customer.ts
export interface CustomerRequest {
    name: string;
    email: string;
    phone: string;
    birthDate?: string;
    address?: string;
    status?: string;
}
```

이번엔 **실패 경로 타입**을 같은 파일 또는 `types/apiError.ts` 에 추가한다.

## 아주 쉽게

백엔드가 보낸 쪽지의 칸 이름과, 프론트가 읽으려는 칸 이름이 같아야 한다.

- 서버: `{ "message": "...", "errors": { "name": "..." } }`
- 프론트 타입: `message`, `errors`  
  이걸 `msg`, `fields` 로 적으면 TypeScript 가 화를 안 낼 수도 있다.  
  **실행 때** 칸이 비어 보인다. 타입이 틀려서가 아니라, 이름이 달라서다.

타입은 경찰이 아니라 **약속 메모**다.  
메모와 실제 JSON 을 네가 맞춰야 한다.

## 라라벨로 번역

| 여기 | 라라벨 + Blade |
|------|----------------|
| `ApiError` 타입 | `$errors->first('name')` — 서버가 HTML에 이미 찍어 줌 |
| axios `catch` 에서 `response.data` | Blade 는 새 페이지라 catch 가 필요 없음 |
| 필드 아래 빨간 글씨 | `@error('name')` |

Blade 는 서버가 그림을 다시 그린다.  
React 는 **네가 data 를 꺼내서** 그림을 그린다. 이 유닛이 SPA 의 핵심이다.

## 미션 5

1. 에러 JSON 용 TypeScript 타입을 만든다.
2. axios 에러인지 확인하고 data 를 꺼내는 **작은 함수**를 만든다.  
   (`customerApi.ts` 또는 `api/error.ts` — 위치는 네가 정한다.)
3. **프론트 1차 검사(`if (!name.trim())`)를 잠시 끄거나 우회**해서, 빈 값이 서버까지 가게 해 본다.  
   그래야 400 JSON 을 화면에서 확인할 수 있다. 확인 후 1차 검사를 다시 켜도 된다.
4. `CustomerCreate` 가 400 이면 필드 이유를, 그 외 실패면 `message` 또는 상태 코드를 보여 준다.
5. `CustomerEdit` 가 없는 id (`/customers/999999/edit`) 로 열리면 404 안내 + 목록 링크. 폼을 그리지 않는다.

**완료 기준**

- [ ] 네트워크 탭의 에러 JSON 과 화면 글자가 **같은 내용**이다 (하드코딩 문장만 아님)
- [ ] 400 일 때 최소 한 필드의 이유가 보인다
- [ ] 없는 고객 수정 URL → 빈 폼이 아니다
- [ ] 정상 등록/수정은 그대로다
- [ ] `any` 로 에러를 때려잡지 않는다. 타입을 쓴다

**힌트**

- 검색어: `axios isAxiosError`, `AxiosError<너의에러타입>`, TypeScript `interface`.
- `err` 는 `unknown` 으로 두는 편이 안전하다. 바로 `err.response` 를 찍으면 TS 가 막을 수 있다. 그게 정상이다.
- 필드 에러를 input 바로 아래에 그릴지, 상단 박스에 모을지는 자유. 처음엔 상단 박스가 쉽다.
- `CustomerCreate.tsx` 에 `if (!phone.trim())` 다음 `return` 이 빠져 있는 줄이 있다. 이번 기회에 **왜 버그인지** 스스로 고치라. (미션의 일부로 인정)

# 유닛 6. 같은 계약을 상품에 옮긴다 (전이 = 습득 확인)

## 개념

고객에서 한 일이 진짜 지식이려면, **힌트 문서 없이** 상품에도 같은 일이 되어야 한다.

옮길 것:

- Request 검증
- 없는 id → 404 JSON (이미 만든 전역 핸들러가 상품 예외도 잡는가?)
- 프론트 등록/수정이 서버 메시지를 보여 주는가
- (선택) 상품명 검색. 시간은 남으면.

옮기지 말 것:

- 고객 이메일의 unique / 409. 상품에는 다른 규칙이 있을 수 있다. 네가 정하라.
- 새 페이지, 새 테이블.

## 아주 쉽게

수학에서 사과 문제로 덧셈을 배웠으면, 배 문제로도 덧셈이 되어야 한다.  
배 문제에서 다시 교과서를 베끼면, 아직 덧셈을 모르는 것이다.

상품 폴더를 열고, 고객에서 한 일의 **목록만** 옆에 두고 옮겨라.  
고객 파일을 통째로 복사하지 마라. 한 줄씩 이유를 생각하며 옮겨라.

## 라라벨로 번역

한 Resource 에 FormRequest + API Resource 를 적용한 뒤, 다음 Resource 에 같은 패턴을 적용하는 것과 같다.  
전역 Exception Handler 는 **한 번만** 있으면 두 리소스에 동작해야 한다. 그게 전역의 의미다.

## 미션 6

이 유닛에는 파일 목록을 일부러 적지 않는다. 네가 찾는다.

1. 상품 Request 검증 규칙을 스스로 정하고 붙인다. (이름·보험사·유형·월 보험료를 떠올려라)
2. 없는 상품 id 가 404 JSON 인지 Postman으로 확인한다.  
   안 되면: 상품 Service 가 던지는 예외를 전역 핸들러가 못 잡는 것이다. 원인을 찾아라.
3. 상품 등록/수정 화면에 서버 에러 표시를 붙인다. 고객 쪽 헬퍼를 **재사용**하라. 복사하지 마라.
4. 상품 행복 경로와 고객 행복 경로를 둘 다 클릭해서 회귀 확인한다.

**완료 기준**

- [ ] 빈 상품 POST → 400 + 필드 에러
- [ ] `GET /api/insurance-products/999999` → 404 JSON
- [ ] 상품 등록 화면이 서버 메시지를 보여 준다
- [ ] `/` 와 `/customers` 의 기존 CRUD 가 산다

**힌트**

- 월 보험료는 숫자다. “비어 있음”과 “0보다 작음”은 다른 규칙이다.
- 전역 핸들러가 `NotFoundException` 만 잡는데 상품은 아직 `IllegalArgumentException` 이면, 상품만 500이 남는다. 이 경험이 유닛 3을 완성한다.

# 유닛 7. 졸업 시험 — 이메일 중복과 계약 한 장

## 개념

검증(400)은 “칸이 이상하다.”  
중복(409)은 “칸은 맞는데, **지금 세상 상태**와 싸운다.”

- 400: 이메일 칸이 비었거나 `abc` 다
- 409: `minsu@example.com` 은 형식도 맞고, 이미 다른 고객이 쓰고 있다

이 구분을 할 수 있으면, REST를 성공 경로가 아니라 **상태 기계**로 보기 시작한 것이다.

Repository 에 “이 이메일이 이미 있나?” 를 묻는 메서드가 필요하다.  
Service 의 `create`(그리고 원하면 `update`) 에서, 있으면 예외를 던진다.  
전역 핸들러가 그 예외를 409 JSON 으로 바꾼다.  
프론트 등록 폼이 그 메시지를 보여 준다.

`update` 에서 자기 자신의 이메일은 중복이 아니다. 이 한 줄이 졸업 문제의 함정이다.

## 아주 쉽게

교실에 “민수”가 이미 있다.

- 출석부에 이름을 안 쓰면 → 선생님: “이름을 써.” (400)
- 새 아이가 자기 이름을 민수라고 쓰면 → 선생님: “그 이름은 이미 있어.” (409)
- 원래 민수가 자기 이름을 다시 민수로 저장하면 → “그래, 너잖아.” (200)

“이미 있어”를 누가 아나? 출석부(DB)를 보는 사람(Service)이다.  
DTO 어노테이션만으로는 다른 아이 이름을 알 수 없다.

## 라라벨로 번역

| 여기 | 라라벨 |
|------|--------|
| `existsByEmail(String email)` | `Customer::where('email', $email)->exists()` |
| 409 예외 | `abort(409, '...')` / 커스텀 exception |
| update 시 자기 자신 제외 | `unique:customers,email,{id}` 룰 |

컬럼에 `unique = true` 를 달면 DB가 막는다.  
그래도 **409 JSON** 은 네가 예외를 잡아야 한다. DB 예외를 그대로 주면 또 500이 된다.

이번 순환 권장:  
먼저 Service 에서 `exists` 로 막고 409를 보낸다.  
Entity `unique` 는 선택. 넣으면 “이중 자물쇠”가 된다. 넣기 전에 `ddl-auto=update` 가 기존 중복 데이터에서 실패할 수 있음을 기억하라.

## 미션 7

1. 같은 이메일로 고객을 두 번 POST 한다.  
   - 첫 번째: 201  
   - 두 번째: **409** + 계약 JSON (500 아님, 201 아님)
2. 기존 고객을 수정할 때 **자기 이메일 그대로 저장**하면 200.
3. 다른 고객의 이메일로 바꾸면 409.
4. 등록 화면에서 중복 이메일을 내면, 서버 `message` 가 빨간 글로 보인다.
5. 노트에 **최종 계약서**를 한 장으로 적는다. (유닛 1 초안을 실제 코드에 맞게 고친다)
6. 상품·고객 행복 경로를 한 번씩 더 클릭한다.

**완료 기준**

- [ ] 위 1~4가 Postman + 브라우저에서 된다
- [ ] 유닛 2~6 이 회귀하지 않았다 (빈 값 400, 없는 id 404, 검색, 상품 검증)
- [ ] 최종 계약서를 이 문서 위에 적지 말고, 네 노트/파일에 적었다
- [ ] 누군가 “왜 400과 409를 나누나?” 라고 물으면 민수 이야기로 답할 수 있다

**힌트**

- 검색어: `existsByEmail`, `existsByEmailAndIdNot`, `@ExceptionHandler` 409.
- update 함정: “이메일 존재?” 만 보면 자기 자신을 409로 친다. `id` 가 다른 행만 보면 된다.
- 동시 요청 두 개가 같은 이메일을 넣는 경합은 이번 범위가 아니다. 혼자 Postman 치는 수준만 막으면 된다.
